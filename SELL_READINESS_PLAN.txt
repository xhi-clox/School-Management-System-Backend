PURPOSE
-------
This document lists everything that must be done to move this codebase from
"working software that one school uses" to "software that can legally and
safely be sold to paying schools in Bangladesh".

It is ordered by dependency. Do NOT start a later phase before the phase above
it is complete and verified. Phases 1 and 2 gate all revenue. Phase 3 gates
scale. Phase 6 gates credibility.

HOW TO USE
----------
Each task is written as:
  [ ] N.N  TITLE
        FILE   : path relative to C:\Users\Walton\Documents\SMS-Backend
        WHERE  : line numbers / symbol (line numbers are from the current
                 9,413-line index.ts; re-verify before editing)
        DO     : the change required
        WHY    : the commercial reason it blocks selling
        VERIFY : the command or manual check that proves it is done

Effort estimates assume ONE developer working part-time (8-12 hours/week).
Verify the current line numbers before editing; index.ts changes often.

SECTION 0 - DECISIONS ALREADY MADE (do not relitigate these)
--------------------------------------------------------------------------------

SEGMENT     : Private schools, 200-800 students. First priority city Dhaka,
              then Chattogram, then secondary cities.
PRICING     : Annual licence, paid UP FRONT. No monthly billing, no auto-debit.
CHANNEL     : Founder-led direct sales. On-site demo, data migration, training.
CAPACITY    : Solo, part-time. Every task is scoped so support time stays low.
BRANDING   : "SMS" means School Management System. There is NO telecom product,
              NO bulk SMS, NO WhatsApp API product, NO BTRC A2A licence needed.
              Remove all messaging/SMS branding and all messaging claims.
WEDGE       : Fee collection and reconciliation. "Stop chasing fees. Know exactly
              who has not paid, every day, without a single phone call to a
              parent." This is the buying reason. Modules are not.

SECTION 1 - VERDICT: CAN YOU SELL THIS TODAY?
--------------------------------------------------------------------------------

NO. Three hard blockers, all verified in the source code on 2026-10-16.

BLOCKER 1 - Around 110 of 206 API routes have NO authentication.
  Anyone on the internet can read every student record, every result, your
  payroll and your finance ledger, and can write invoices, payments,
  announcements and attendance. Confirmed unauthenticated examples:
    index.ts:6832  GET  /finance/transactions
    index.ts:6972  GET  /finance/reports/summary
    index.ts:6539  GET  /invoices
    index.ts:4768  GET  /salaries
    index.ts:4773  POST /salaries/process
    index.ts:4834  DEL  /salaries/:id
    index.ts:2387  GET  /results
    index.ts:2401  POST /results/bulk
    index.ts:1124  GET  /students/logins   (and PUT/POST/DELETE siblings)
    index.ts:5121  GET  /attendance
    index.ts:5862  POST /attendance/save
    index.ts:4690  GET  /fees
    index.ts:6722  GET  /staff
    index.ts:4985  GET  /announcements
    index.ts:5869+ GET  /student/*         (entire student portal)
    index.ts:202   GET  /test-db

  Commercial impact: one security-conscious headmaster finds this in a demo
  and the deal dies, then tells the market. This is existential.

BLOCKER 2 - There is a hardcoded admin backdoor password.
  index.ts:7599
      password === 'fresh_password_2026'
  grants admin access to any known email address. Also:
    index.ts:7639-7646 teacher with no login record can sign in with
                     'password', 'test', '123456', their employeeId, or the
                     local part of their email.
    index.ts:7668   student passwords compared in PLAINTEXT.
    index.ts:7689   a student with no login row accepts ANY password.

BLOCKER 3 - There is no multi-tenancy at all.
  There is no schoolId column anywhere in prisma/schema.prisma. The Institute
  model (schema.prisma:843) is a single global profile row. School #2 would
  see school #1's students. You cannot onboard a second paying customer until
  this is built. Multi-tenancy is not a feature; it IS the product.

Plus: the landing page currently makes claims that are false (see Section 6).
Promising a 14-day free trial and a pricing page that do not exist is a
fraudulent-advertising and consumer-trust risk in a small, word-of-mouth
market.
